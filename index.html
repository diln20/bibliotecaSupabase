01 · SUPABASE ACADEMY

Supabase desde cero hasta una API completa

PostgreSQL, SQL, API REST, JavaScript, autenticación, seguridad, archivos y un proyecto progresivo de estudiantes.

💡 EXPLICACIÓN FÁCIL · Antes del código
🙂 En palabras simples

02 · FUNDAMENTOS

Antes de Supabase: Web, HTTP, API y JSON

Entiende primero qué problema resuelve una API y cómo viajan los datos.

💡 EXPLICACIÓN FÁCIL · Antes del código
🙂 En palabras simples

Una API es una forma acordada para pedir o enviar datos. El navegador no necesita saber cómo está guardada internamente cada fila.

🏠 Ejemplo cotidiano

Es como pedir un libro en una biblioteca: tú das una solicitud; el bibliotecario consulta el catálogo y te entrega una respuesta.

⚙️ ¿Qué pasa por detrás?

El cliente hace una petición HTTP. La API interpreta método, ruta, parámetros y credenciales; luego consulta la base de datos y responde normalmente con JSON.

🧠 Qué debes recordar

GET consulta, POST crea, PATCH modifica y DELETE elimina. JSON es un formato para representar datos.

03 · SUPABASE

¿Qué es Supabase?

Conoce las piezas antes de entrar al Dashboard.

💡 EXPLICACIÓN FÁCIL · Antes del código
🙂 En palabras simples

Supabase es una plataforma de backend que gira alrededor de una base de datos PostgreSQL. Incluye Data API, Auth, Storage, Realtime y otras herramientas.

🏠 Ejemplo cotidiano

Es como alquilar un local que ya trae bodega, cámaras, recepción y sistema de acceso: todavía debes organizar tu inventario y definir quién puede entrar.

⚙️ ¿Qué pasa por detrás?

Cada proyecto recibe PostgreSQL. La API se refleja desde el esquema de la base de datos y las políticas de PostgreSQL participan en la seguridad.

🧠 Qué debes recordar

La base de datos sigue siendo el centro. Supabase facilita acceso y servicios, pero el diseño de tus tablas sigue siendo tu responsabilidad.

06 · BASE DE DATOS

Tipos de datos, PRIMARY KEY, NULL y DEFAULT

Elige qué puede guardarse en cada columna y cómo identificar filas.

💡 EXPLICACIÓN FÁCIL · Antes del código
🙂 En palabras simples

Cada columna debe decir qué tipo de valor acepta. Una clave primaria identifica una fila sin ambigüedad.

🏠 Ejemplo cotidiano

La cédula identifica a una persona; un campo “activo” funciona como interruptor; una fecha registra un momento.

⚙️ ¿Qué pasa por detrás?

PostgreSQL valida tipos y restricciones antes de guardar. Los valores por defecto se aplican cuando no envías un dato.

🧠 Qué debes recordar

PRIMARY KEY identifica; NOT NULL obliga; DEFAULT completa automáticamente.

Primera tabla
create table public.programas (
  id bigint generated by default as identity primary key,
  codigo text not null,
  nombre text not null,
  activo boolean not null default true,
  created_at timestamptz not null default now()
);

id: PostgreSQL genera un número automáticamente y lo usa como PRIMARY KEY.

nombre: no puede quedar vacío a nivel de NULL.

activo: si no envías valor empieza en true.

created_at: guarda el momento de creación.

🏠 Ejemplo cotidiano

🧠 Qué debes recordar

CRUD en SQL
insert into public.programas (codigo, nombre)
values ('SIS', 'Ingeniería de Sistemas');

select * from public.programas;

update public.programas
set nombre = 'Sistemas'
where id = 1;

delete from public.programas
where id = 1;
⚠️ Cuidado: un UPDATE o DELETE sin WHERE puede afectar muchas filas.

09 · BASE DE DATOS

Relaciones 1:N y JOIN

Consulta datos relacionados sin duplicarlos.

💡 EXPLICACIÓN FÁCIL · Antes del código
🙂 En palabras simples

Una relación 1:N significa que un programa puede tener muchos estudiantes, pero cada estudiante de este modelo pertenece a un programa.

🏠 Ejemplo cotidiano

Un curso puede tener muchos alumnos. En vez de escribir el nombre del curso 30 veces, cada alumno guarda el id del curso.

⚙️ ¿Qué pasa por detrás?

La foreign key mantiene integridad. Un JOIN combina temporalmente columnas de tablas relacionadas para responder una consulta.

🧠 Qué debes recordar

FK = relación guardada; JOIN = consulta que combina.

JOIN estudiantes + programas
select
  e.id,
  e.nombre as estudiante,
  e.correo,
  p.nombre as programa
from public.estudiantes e
inner join public.programas p on p.id = e.programa_id
order by e.nombre;

10 · SQL

SELECT, WHERE, ORDER BY, LIMIT y agregaciones

Aprende a hacer preguntas útiles a la base de datos.

💡 EXPLICACIÓN FÁCIL · Antes del código
🙂 En palabras simples

No siempre quieres todas las filas. Los filtros te permiten pedir solo los datos necesarios.

🏠 Ejemplo cotidiano

En una lista de 10.000 estudiantes puedes pedir solo los activos, ordenados por nombre, y mostrar 20.

⚙️ ¿Qué pasa por detrás?

PostgreSQL filtra y ordena en el servidor. Eso evita descargar datos que el cliente no necesita.

🧠 Qué debes recordar

Filtra en la base de datos cuando sea posible; no traigas todo para filtrar después en JavaScript.

Consultas frecuentes
-- activos
select id, nombre, correo
from public.estudiantes
where activo = true
order by nombre asc
limit 20;

-- cantidad por programa
select programa_id, count(*) as total
from public.estudiantes
group by programa_id
order by total desc;

11 · BASE DE DATOS

UNIQUE, CHECK e índices

Protege la calidad de los datos y prepara consultas rápidas.

💡 EXPLICACIÓN FÁCIL · Antes del código
🙂 En palabras simples

Las restricciones impiden guardar datos inválidos. Los índices ayudan a encontrar filas sin revisar toda la tabla.

🏠 Ejemplo cotidiano

UNIQUE funciona como “no aceptamos dos documentos iguales”. Un índice se parece al índice alfabético de un libro.

⚙️ ¿Qué pasa por detrás?

PostgreSQL valida constraints al escribir. Un índice crea una estructura adicional que acelera determinadas búsquedas, con costo de almacenamiento y escritura.

🧠 Qué debes recordar

No todo necesita índice. Empieza por claves, campos únicos y columnas consultadas con frecuencia.

Restricciones e índices
alter table public.programas
add constraint programas_codigo_unique unique (codigo);

create index estudiantes_programa_id_idx
on public.estudiantes(programa_id);

create index estudiantes_created_at_idx
on public.estudiantes(created_at desc);

13 · BASE DE DATOS

Transacciones y consistencia

Comprende qué pasa cuando varias operaciones deben completarse juntas.

💡 EXPLICACIÓN FÁCIL · Antes del código
🙂 En palabras simples

Una transacción agrupa cambios para que se confirmen juntos o se deshagan si algo falla.

🏠 Ejemplo cotidiano

Una transferencia bancaria no debería descontar dinero sin también abonarlo al destino.

⚙️ ¿Qué pasa por detrás?

PostgreSQL ofrece transacciones ACID. Desde clientes HTTP, operaciones complejas que deban ser atómicas suelen encapsularse en funciones o lógica de servidor.

🧠 Qué debes recordar

Si dos cambios deben ser “todo o nada”, no los trates como acciones independientes sin pensar en atomicidad.

Idea de transacción
begin;

update public.estudiantes
set activo = false
where id = 10;

insert into public.auditoria (evento, entidad_id)
values ('DESACTIVADO', 10);

Row Level Security (RLS)

Define qué filas puede consultar o modificar cada usuario.

💡 EXPLICACIÓN FÁCIL · Antes del código
🙂 En palabras simples

RLS son reglas que PostgreSQL evalúa por fila. Una tabla puede permitir que un usuario vea sus propios datos pero no los de otra persona.

🏠 Ejemplo cotidiano

Dos estudiantes entran al mismo archivo, pero el guardia les entrega solo las carpetas autorizadas.

⚙️ ¿Qué pasa por detrás?

Grants indican si un rol puede ejecutar una operación sobre la tabla; las policies RLS determinan sobre qué filas puede hacerlo.

🧠 Qué debes recordar

RLS activado sin políticas apropiadas bloquea el acceso desde la API. Eso suele ser más seguro que abrir todo.

Primera policy
-- 1) Activa RLS en las tablas expuestas
alter table public.programas enable row level security;
alter table public.estudiantes enable row level security;

-- 2) Empieza con privilegios mínimos para la fase de lectura
revoke all on table public.programas from anon, authenticated;
revoke all on table public.estudiantes from anon, authenticated;
grant select on table public.programas to anon, authenticated;
grant select on table public.estudiantes to anon, authenticated;

-- 3) Policies de lectura del ejercicio
create policy "programas visibles"
on public.programas
for select
to anon, authenticated
using (activo = true);

create policy "estudiantes activos visibles"
on public.estudiantes
for select
to anon, authenticated
using (activo = true);
Para producción: no uses políticas amplias solo para evitar errores 401/403. Diseña acceso según tu caso real y concede a cada rol únicamente las operaciones necesarias.

26 · STORAGE

Archivos con Supabase Storage

Guarda avatares o documentos fuera de las tablas.

💡 EXPLICACIÓN FÁCIL · Antes del código
🙂 En palabras simples

Storage está pensado para archivos. En la base de datos normalmente guardas metadatos o la ruta, no el contenido pesado del archivo.

🏠 Ejemplo cotidiano

La base de datos es el catálogo; el depósito de cajas es Storage.

⚙️ ¿Qué pasa por detrás?

Los archivos se organizan en buckets y rutas. Las políticas de Storage controlan operaciones sobre objetos.

🧠 Qué debes recordar

Usa buckets separados cuando necesites reglas de acceso distintas.

Subir un avatar
const file = document.querySelector('#avatar').files[0];
const path = `${user.id}/${crypto.randomUUID()}-${file.name}`;

const { data, error } = await db.storage
  .from('avatars')
  .upload(path, file, { upsert: false });

27 · REALTIME

Cambios en tiempo real

Actualiza una pantalla cuando cambian filas sin recargar manualmente.

💡 EXPLICACIÓN FÁCIL · Antes del código
🙂 En palabras simples

Realtime permite escuchar eventos de cambios de base de datos para determinadas tablas y filtros.

🏠 Ejemplo cotidiano

Es como suscribirte a un tablero: cuando alguien cambia una ficha, recibes un aviso.

⚙️ ¿Qué pasa por detrás?

El cliente abre una suscripción. Cuando ocurre un evento configurado, tu callback recibe información y puede refrescar la interfaz.

🧠 Qué debes recordar

Úsalo cuando realmente necesites datos vivos; no toda pantalla requiere una suscripción permanente.

Escuchar cambios
const canal = db
  .channel('estudiantes-cambios')
  .on(
    'postgres_changes',
    { event: '*', schema: 'public', table: 'estudiantes' },
    () => cargarEstudiantes()
  )
  .subscribe();

28 · POSTGRESQL

Funciones SQL y RPC

Mueve operaciones de datos complejas a una función controlada.

💡 EXPLICACIÓN FÁCIL · Antes del código
🙂 En palabras simples

Cuando una operación necesita varias consultas o una lógica cercana a los datos, puedes crear una función PostgreSQL y llamarla por RPC.

🏠 Ejemplo cotidiano

En vez de hacer cinco viajes a la bodega, entregas una orden que el encargado ejecuta allí dentro.

⚙️ ¿Qué pasa por detrás?

La función se ejecuta en PostgreSQL y puede exponerse a la API según permisos. Debes revisar cuidadosamente seguridad y search_path.

🧠 Qué debes recordar

No conviertas todo en RPC. Para CRUD sencillo, las operaciones directas suelen ser más claras.

Función PostgreSQL
create or replace function public.total_estudiantes_activos()
returns bigint
language sql
stable
as $$
  select count(*)
  from public.estudiantes
  where activo = true;
$$;
Llamar por RPC
const { data, error } = await db.rpc('total_estudiantes_activos');
console.log(data);
